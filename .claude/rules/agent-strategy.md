# 에이전트 모델 전략

Task 도구로 서브 에이전트를 생성할 때 아래 전략에 따라 운영할 것.

## 핵심 원칙: 최소 컨텍스트 + 이벤트 드리븐

1. **선택적 프롬프트**: 각 에이전트에게 해당 작업에 필요한 최소 정보만 전달
2. **파일 경로 참조**: 대량 데이터는 프롬프트에 포함하지 않고, 파일 경로를 전달하여 에이전트가 직접 읽게 함
3. **resume 활용**: 동일 에이전트에 후속 작업이 필요하면 새 에이전트 대신 resume으로 컨텍스트 유지
4. **에러 감지**: PostToolUse 훅이 OS 임시 디렉토리의 claude-agent-log.jsonl 에 에이전트 실행 결과를 자동 기록 (macOS: /tmp/, Windows: %TEMP%)

## 수집 → 분석 파이프라인

**1단계 - 정보 수집** → `collector` 에이전트 (Haiku)
- 여러 collector를 병렬로 실행하여 속도 확보
- 프롬프트: 검색 대상 + 검색 조건만 (배경 설명 최소화)

**2단계 - 분석/생성** → 전문 에이전트 (Sonnet)
- `custom-code-reviewer`: 코드 리뷰 (보안, 성능, 컨벤션)
- `db-analyst`: DB 스키마, 마이그레이션, 쿼리 분석
- `draft-writer`: Jira 티켓 + Confluence 문서 초안 생성 (실제 등록은 메인 에이전트가 MCP로 수행)
- 프롬프트 구성:
  - 1단계 결과가 큰 경우 → 파일에 기록 후 경로만 전달
  - 1단계 결과가 작은 경우 → 프롬프트에 직접 포함

**3단계 - 종합 판단** → `architect` 에이전트 (Opus)
- 프롬프트: 결론/요약 + 판단에 필요한 제약조건만

## 커스텀 에이전트 vs 플러그인 에이전트 선택 기준

유사한 역할의 에이전트가 있을 때 아래 기준으로 선택할 것:

- 코드 리뷰: `custom-code-reviewer` 우선 (프로젝트 컨벤션 반영됨). 플러그인 `feature-dev:code-reviewer`는 confidence 기반 필터링이 필요할 때 사용
- 코드베이스 탐색: 단순 파일/패턴 검색은 `collector`, 실행 경로 추적 등 심층 분석은 `feature-dev:code-explorer`
- 아키텍처 설계: 종합 판단이 필요하면 `architect` (Opus), 기존 패턴 기반 구현 설계는 `feature-dev:code-architect`
- DB 분석: `db-analyst` (전용 에이전트)
- 문서 초안: `draft-writer` (전용 에이전트)
- 코드 정리: `code-simplifier` (플러그인 전용)

## 프롬프트 구성 규칙

에이전트 프롬프트는 다음 구조를 따를 것:

```
## 작업 목표
(1-2문장으로 명확하게)

## 입력 데이터
(직접 포함 또는 "파일 경로를 읽어서 확인해" 형태)

## 출력 형식
(기대하는 결과물의 형식을 명시)
```

**금지 사항:**
- 전체 대화 히스토리를 프롬프트에 포함하지 말 것
- "이전에 이런 논의가 있었다" 같은 배경 설명 최소화
- 에이전트가 알 필요 없는 정보는 제외

## 에러 처리 및 폴백

- 오케스트레이터(메인 에이전트)가 에이전트 결과를 직접 평가
- 불충분한 결과 → resume으로 동일 에이전트에 보완 요청 (새 에이전트 생성보다 효율적)
- resume으로 해결 불가 시 → 상위 모델로 에스컬레이션 (이전 시도 결과 + 실패 사유 전달)
- 에이전트 내부 오류(크래시) → 사용자에게 즉시 보고, 재시도 여부 확인
- 2단계 이상 에스컬레이션 시 사용자에게 상황 보고

## 작업 상태 표시 규칙
- TaskCreate 시 `activeForm`에 반드시 모델명 태그를 포함할 것
- 형식: `[모델명] 작업 내용`
- 예시:
  - `[Haiku] 관련 파일 수집 중`
  - `[Sonnet] 코드 분석 중`
  - `[Opus] 아키텍처 설계 중`
